# Agent 全链路追踪与修复闭环方案

## 1. 目标

平台测试的是**外部 Agent**，不是平台自身的 AI。平台需要回答四个问题：

1. 给 Agent 的命令是什么？
2. Agent 做了什么（意图、路由、工具、检索、LLM）？
3. Agent 最后反馈了什么？
4. 反馈是否正确；如果错误，怎么修、修完是否回归通过？

## 2. 总体链路

```text
测试用例/命令
  → Agent 适配器（HTTP / CLI / WebUI / App）
  → trace_id 贯穿
  → trace_spans（command / agent / llm / tool / retrieval / final）
  → 规则判定 + wb2api LLM Judge + 人工评审
  → 失败修复工单
  → 修复前后回归对比
  → 自动生成 docs/fix-experience/v1.0---<名称>-fix经验积累.md
```

## 3. 关键原则

- **平台独立判定**：不信任 Agent 自报的 `status/answer`；判定必须基于命令、期望、工具结果、检索证据和最终回答。
- **可复现**：每次运行保存 trace_id、输入、输出、模型、耗时、token、证据 span。
- **可回归**：修复工单必须关联修复前后两次 run；回归不通过不能关闭。
- **可沉淀**：每次修复生成一篇经验文档；同一问题再次出现追加“修复轮次”，不覆盖历史。
- **先真后全**：先跑通 HTTP/CLI 真链路，再接 WebUI/App；模拟执行必须明确标注，不能伪造成成功。

## 4. 数据模型

详见 `docs/agent-trace-contract.md` 第 2 节。核心表：

- `agent_targets`：被测 Agent 配置
- `agent_test_cases`：命令、期望、规则检查
- `agent_runs`：一次运行
- `trace_spans`：全链路 span
- `trace_artifacts`：截图/视频/trace.zip/日志
- `run_evaluations`：规则/LLM/人工判定
- `fix_records`：修复工单与经验文档路径

## 5. 判定策略

### 5.1 规则判定

覆盖：状态、意图、Agent、工具调用、检索命中、文本包含/正则、耗时、敏感信息、证据 grounded。

### 5.2 LLM Judge

- 使用本机 zcode 的 wb2api（OpenAI 兼容，模型 `deepseek-v4.1-flash`）。
- 输入：命令、期望、最终回答、工具结果、检索证据。
- 输出固定 JSON：`verdict / score / reasons / evidence / missing_facts / hallucination`。
- Judge 不可用时返回 `unavailable`，转人工，不默认通过。
- 每次 Judge 记录 prompt/response 和 token，作为 `judge` span。

### 5.3 人工评审

评审者可标记通过/失败/待复核，填写原因；人工结论可覆盖 LLM 判定，操作写审计。

## 6. 修复经验文档

- 目录：`docs/fix-experience/`
- 文件名：`v1.0---<名称>-fix经验积累.md`
- 同一问题再次修复：追加 `## 修复轮次 N`，不覆盖原文件。
- 索引：`docs/fix-experience/README.md`
- 模板：`docs/fix-experience/_template.md`
- 章节：基本信息、问题现象、复现方式、链路追踪、根因分析、修复方案、回归验证、经验总结、附件。

## 10. 验收

- 每次运行有唯一 trace_id，能看到 command → agent → llm/tool/retrieval → final。
- 规则/LLM/人工三方判定可见，失败有证据。
- 失败 → 修复 → 重跑 → 回归通过 → 生成 md。
- `pnpm exec tsc --noEmit`、`pnpm test`、后端 pytest 通过。
- trace 中不出现 API Key、Authorization、Cookie。
